# SpectreReplay

[English](README.md) | **简体中文**

《A Dance of Fire and Ice》的关卡录制、回放与视频渲染模组——**正常游玩即自动记录，回放与出片都在游戏里完成**。

SpectreReplay 是一个 UnityModManager 模组（模组 Id `com.spectre.replay`）。你在正常游玩时，它会自动把这一局的按键与判定录下来；之后能在游戏里把这份录制原样放回去，也能把它渲染成带音轨的视频文件。回放和渲染都不是"另算一遍"：两者都跑在游戏本体上，你看到的画面就是游戏自己产出的画面。

> **关于「要不要重跑一遍」**：录制**不需要**——开着模组正常玩，文件自己就有了。但**回放和渲染需要**：回放要重开那一关才会播放，渲染会在关卡里把回放重跑一遍逐帧抓取。这是它有意的设计（见下方「视频渲染」），不是缺陷。

## 功能

### 录制

- **正常游玩时自动记录。** 录制不需要你先按下什么、也不需要为它单独跑一遍关卡——模组在进关前就已经装好，从这一局的第一帧开始采集。
- **自动保存。** 通关的一局会自己落盘，不用点任何按钮。
- **手动保存。** 热键可以在关卡中途把当前这一局存下来，包括你有意放弃的那些尝试。
- **取消保存。** 另一个热键把正在录的这一局丢掉——留给你不想放进文件夹的热身和重试。
- **失败与遗漏保护。** 全自动跑完的局、有失误的局都可以按策略跳过不存；反过来，失败（没过关）的局也能照样保存。
- **备份。** 可选地为每份回放多留一份副本，坏一个文件不至于把录制丢掉。副本是从写好的主文件直接复制的（不再重跑一遍保存流程），主保存本身失败时不会走备份。
- **键盘音（可选）。** 把麦克风输入当成一条独立音轨录进这一局，回放时按当时的按键重新敲出来。它存在回放文件**里面**（默认 16 kHz，可以降到 8 kHz 换体积），所以回放换台机器也带着按键声，不必在旁边再放一个 wav 文件。

### 回放

- **在游戏内回放。** 录制数据驱动的是游戏本体：命中时机、地板、生命周期都按帧还原。
- **从文件载入。** 文件列表会列出保存目录里的回放，点一份就装好待放。落盘有两种容器变体：`.sprp`（加密，默认）与 `.psprp`（不加密，调试用）。
- **直接打开对应关卡。** 载入的回放知道自己录自哪张谱面，模组可以替你打开那一关——自制谱和官方关卡都一样——并在就绪后定位到起始砖。
- **卸载回放。** 不离开关卡也能把装好的回放卸掉。
- **按键注入。** 按键被注入到游戏的输入层，游戏对它的反应与对你键盘的反应完全一致。同步输入与异步输入两条路都支持；游戏开启异步输入后，时间戳取自游戏自己的输入戳而不是帧边界，精度明显更好。
- **列表搜索。** 回放攒多了不必靠肉眼翻：输入即按文件名筛选，不区分大小写，Esc 清空。云备份那一栏有同一套搜索框，两边各筛各的——云端有、本地还没回填的那些不会因为本地筛选而消失。
- **每一份的键盘音可以单独调。** 音量、静音、相对谱面的时间偏移，三项都只作用于这一份回放；拖动即时可听，满意了点「保存到回放文件」才写进文件本身（不生成副本），没设过的项继续跟随全局。也能把这份回放的键盘音导出成 wav，放在保存目录的 `keybdsound` 下。
- **从云端直接回放。** 云端的回放不必先下载到本地目录：点「回放」就从云端字节直接播放，一个字节都不落地。点名字只是展开详情（歌名、难度、判定分布、逐击偏差），不会把正在放的那局顶掉。

### Steam 云备份

- **回放跟着 Steam 云走。** 键盘音是嵌在回放文件里的，所以云端通常只放一份回放本体；只有键音没能嵌进去（旧版本录的，或压缩后仍超限而退回旁挂 wav）时，才会连同那份同名 wav 一起传。换机器或重装之后，第一次启动会把本地缺的自动补回来——按文件名比对，本地已有的同名文件一概不覆盖。
- **同步可以关。** 关掉之后不再往云上写，本地回放照旧保存；重新打开会把本地已有的补传上去。也可以「全部上传」一次补齐，云端已有且没改动的会跳过，不重复传。
- **配置文件单独存一份。** 模组的 `Configs.json` 可以单独上传，换机器后取回就还原了全部设置。取回前会把本机原文件备份成 `Configs.json.bak`，而且要**点两下**才真做。
- **删云端不动本地。** 删掉的只是云端那一份（连它的键盘音），本地文件保留；接近配额上限时界面会提示先清理旧回放。
- **Steam 只在游戏退出时才真正送出文件**，所以刚录完的回放不会立刻出现在云端。这一条在界面上是照实说的「已写入云端」，没有写成「已同步」。

### 视频渲染

- **把回放渲染成文件。** 重跑一遍回放、逐帧有意捕获，再连同音轨一起编码成视频。
- **两种画面源。** *游戏画面*抓的是游戏显示的内容（含界面），分辨率跟随窗口；*纯净相机*把游戏的三相机链渲染进离屏纹理，不含任何界面元素，分辨率任意，可以超采样。
- **编码器与画质档位。** CPU（libx264）或硬件（NVENC）编码，四档速度/画质；没探到可用的硬件编码器时自动回退到 CPU。
- **四种容器：mp4、mkv、webm、mov。** 视频与音频编码器按容器选（例如 webm 会重编码成 VP9 + Opus）。
- **格式转换。** 输出目录里的视频可以批量转成另一种容器，与"下一次渲染用什么格式"互相独立；已是目标格式的文件会跳过。
- **结尾留白秒数。** 谱面结束后多录几秒，收尾动画不会被切掉。
- **确定性渲染时钟（实验性，默认关）。** 把游戏读到的时间源换成帧号驱动的虚拟时钟，成片里不再有音频时钟抖动。

### 去特效

- **在特效跑起来之前把它们摘掉。** 滤镜与闪光、粒子、装饰物、镜头移动、星球旋转、轨道动画与变色、打击音与长按音、检查点、输入事件、帧率变化、重复事件——每一项都能单独关掉，所以既可以让谱面看起来干净，也能让跑不动的机器渲染得动。
- **在解码处一次性完成。** 事件是从解码后的关卡数据里摘掉的，不是运行期逐个拦事件类型，所以不会留下残余，也不必为此写补丁。
- **不动磁盘上的文件。** 它只改内存里的谱面副本。功能生效期间编辑器默认禁止存盘，避免试听一次就把清干净的谱面写回原文件；要覆盖关卡是另一个开关，默认关。
- **保留被引用的装饰物。** 除非你要求清空**全部**装饰物，被条件事件引用的那些会留下——否则那些分支永远不会触发，谱面看着像做坏了。

### 音频

- **从混音总线精确抓取。** 歌曲、打击音、长按音取自游戏最终的混音总线，而不是靠猜着重混一遍，并作为成片的音轨合成进去。

### 设置界面

- **全自绘控件。** 每一个控件都是模组自己画的——圆角面板（九宫格贴图）、自绘滑条、自绘开关与输入框——所以不受游戏 UI 缩放影响，长得始终一样。
- **悬停说明。** 每一项在悬停时都会解释自己，包括"要这项生效，游戏里必须先开哪个选项"这种前置条件。
- **五个页面**（录制、回放、视频渲染、去特效、关于），热键呼出，界面语言跟随游戏——游戏自带的 **14 种语言**全做了（简中／繁中／英／日／韩／西／葡／法／德／波／捷／罗／俄／越）。
- **提示条停留时长可调。** 屏幕底部提示条自动收起的秒数放在「关于」页（1–10 秒，默认 3 秒）。本模组自己弹的每条提示都跟着它缩放；需要多读一会儿的那几条（失败原因常有两行）在这个基础上再多留 2 秒，所以调大之后它们也跟着变长，不会被写死的秒数卡住。

## 原理

### 补丁层

模组对游戏做的每一件事都通过补丁完成，而补丁是**声明式的**，不靠手写注册。每个补丁方法带一个 attribute，写明目标类型与成员、注入点（前缀／后置／transpiler／finalizer）、优先级、适用的游戏版本区间，以及它属于哪个功能。宿主在加载时扫描这一批声明，对着真实的游戏程序集把目标解析出来，只挂载解析成功且版本在区间内的那些。

关键在于功能开关的实现方式：**谓词在挂载时求值，谓词为假则该补丁根本不会被挂载。** 它不是补丁体里的一句 early `return`，也不是每次调用都查一遍标志位。这个区别正是开关可信的原因：

- 拨开关在**同一拍**生效，上一个状态不会留任何残渣；
- 关掉的功能在游戏里**没有任何被改写的 IL**，既不占开销，也不存在"半个补丁"这种要推理的状态；
- 卸载会把原方法体原样还原，反复开关也不会漂移。

版本门控是同一套机制的一部分。只在某个构建之后才存在的 API、在某个构建改过签名的方法，各自带着自己的版本区间；宿主拿当前游戏构建去比，区间外的一律跳过。解析失败的目标会被收集起来在设置页里如实报出而不是吞掉——因为"补丁静默挂载失败"和"功能就是不好使"在玩家眼里长得一模一样。

### 录制

游玩过程中，录制器每帧采样一次，把这一局编码成紧凑的二进制流：每帧的按键状态与判定结果——命中误差、地板、时间戳——加上还原上下文所需的元信息（谱面身份、难度、速度，以及重算判定窗口所需的逐击上下文）。这段流先压缩（Brotli 质量档 6，外面套一层小包装记下算法号与原文长度），再加密，然后落盘。不足 512 字节的负载、以及压缩后反而更大的负载都直接存原文——包装层让压缩方式逐文件自描述，读侧不必猜。

容器开头是 magic、格式版本号，从第 3 版起还写入密钥派生的迭代次数。新版构建录出的文件会被干净地拒绝，而不是被半解析成一段误导人的数据。

#### 设计要点：容器格式

这里的加密是为了挡住"随手改文件"，不是挡住铁了心要读的人——口令材料就编译在 DLL 里，迭代多少次都改变不了这一点。所以设计针对的是三件**确实可修**的事：

- **密钥派生带盐、带迭代**（PBKDF2-HMAC-SHA256，每文件随机盐）：抬高"从程序集里算回密钥"的成本，并让预计算表失效。
- **每文件随机 IV。** 上游那套用的是从常量字符串派生的固定 IV，加密因此是确定性的：两局内容一样，文件就逐字节一样。这比密钥弱更严重——它把"我有两份相同战绩"变成了可观测事实。
- **encrypt-then-MAC。** HMAC-SHA256 覆盖 magic、版本、迭代次数、盐、IV 与密文，且**先验 MAC 再解密**——被篡改的文件在第一步就被拒，而不是喂给 CBC 产出垃圾（或约 1/256 概率产出能通过填充校验的垃圾）。

第 3 版把迭代次数写进文件头，以后再调不必再破一次格式；第 2 版的迭代次数只能钉死在当年的 6 万次，因为它的头部没存这个值。

读路径**只认这个容器**。更早的两种布局（本模组 2026-10-18 加密重写之前的存量文件，以及同源项目的旧固定密钥格式）都**读不了**——那条兼容回落是被有意删掉的：一份编译进 DLL 的解密例程，等于把钥匙留在锁旁边。

压缩层的版本与容器独立：包装层第一个字节写明算法（原文／gzip／Brotli），而首字节是 `0x1F` 的负载按**包装层之前**那种裸 gzip 流读——引入 Brotli 之前录下的回放是那个布局，所以这条读路径保着。

把负载压小不只是为了文件体积：录制跑在游玩时的主线程上，每帧开销必须有界，文件也要小到能攒下几百局。

### 云备份

Steam 的云端接口只认「文件」，没有查询、没有事务，也没有「哪些是本地新增」这类信息，所以同步只能是文件集合对账：

- 键盘音**优先嵌在回放文件本体**里，所以云端通常只有一份文件要传。只有嵌不进去的（旧版本录的，或压缩后仍超限而退回旁挂）才需要额外那份同名 wav；缺了它画面照放，只是没按键声。
- 回填按文件名比对，**永不覆盖本地同名文件**。云端那份可能是另一台机器的旧写入，本地这份可能是刚录的——两个方向里只有「本地优先」不会吃掉数据。
- 写进云目录不等于已经上传：Steam 到游戏退出才送出。界面因此说「已写入云端」，而不是「已同步」。
- 配置单独存一份、与回放分开，否则「只想还原设置」会变成一次全量拉取。

### 回放

载入时，文件先验 MAC 再解密、解压、解码，得到一条由按键事件与命中上下文组成的时间轴。回放期间，模组把这条时间轴对着游戏自己的帧更新重放：每帧用录制状态覆盖实时状态（行星角度、地板、auto 标志、判定状态），并按录制里记录的时间戳把按键注入输入层。这就是回放看起来和原局**一模一样**而不是"差不多"的原因——真正的判定由游戏对注入的按键跑一遍，画面由当初同一份代码产出。

两条输入路径都支持。旧路把按键事件注入游戏的键盘状态；异步路把输入喂进游戏的异步输入队列，那也正是游戏在开启该选项时用来精确计时的通路。走队列而不是直接伪造键状态，才让时机像人类打的，而不是像卡在帧边界上。

键盘音不走这条流，它是回放文件**尾部的一个可选段**，带自己的段版本上界。这么放的理由是「没录键盘音的人不该付出任何代价」：没用到的回放根本不写这一段，字节与加这个功能之前完全一样；读到不认识的段头（魔数不符或版本高于自己）就整段忽略，前面已经读出来的轨迹与音频照旧完好。每份回放的音量／静音／偏移覆盖值同样存在这一段里，所以它们跟着回放走，而不是留在本机配置里——把文件拷给别人，看到的就是你调好的样子。

### 视频渲染

渲染把回放当成一条胶片，而不是一次实时游玩：

1. **钉死游戏时间轴。** 渲染任务固定一个歌曲位置，每捕获一帧就把它推进整整一个输出帧，于是游戏的各套系统（轨道推进、相机事件、判定、打击音调度）按确定步长推进，与墙上时钟脱钩。
2. **每步抓一帧。** 或者走屏幕抓取，或者把游戏相机链渲染进离屏纹理；转成 ffmpeg 期望的字节排布后推进编码器的 stdin。写管道在后台线程完成，磁盘慢也不会卡住游戏主循环。
3. **每步抓音频。** 同时从游戏的混音总线抓取，写成 32 位浮点 WAV。
4. **收尾合成。** 视频轨与 WAV 按目标容器合成，编码器组合选用该容器真正接受的。

可选的确定性时钟再进一步，直接替换时间源本身：一个 transpiler 改写游戏对音频 DSP 时钟与非缩放时间的读取，让它们返回由帧号推导出的值。游戏随后用这个钉住时钟驱动自己的节拍推进、相机事件与倒计时，代价是动了游戏全局的时间——所以它默认关闭、标注为实验性。

#### 设计要点：音频采集容器的长度必须等于本帧样本数

Unity 的 `AudioRenderer` 从采集环形缓冲里消费的样本数，**就等于你递进去那个数组的长度**。很自然会想到分配一个够大的缓冲、每帧复用，省掉每帧的分配——而这是一种静默失败：数组比本帧可用样本长，读指针就被推过了写指针；从那一刻起采集恒报 0 个可用样本、音频时钟冻结。成片的剩余部分全是静音，而任何地方都不报错。

所以长度必须**恰为**本帧每通道样本数 × 声道数。真实帧长会随音频回调节拍在 128／256／512 之间抖动，长度一变就重建那块非托管缓冲；它走的是非托管内存，重建很便宜。只做拷贝与落盘的托管 `float[]`／`byte[]` 可以放心分桶复用，因为它们的长度对渲染器没有任何语义。**"递给 Unity 的缓冲"与"往里拷贝的缓冲"是两回事**——这个区分就是全部设计。

### 音轨

混音采集在渲染任务开始时启动、结束时停止。无输出不会被立刻判定为失败：先在有界次数内重启采集（切场景时音频回调可能错过最初几帧），都无效才宣告音轨死亡，并给出具体错误，而不是安静地生成一个没有声音的视频。

## 技术栈

- **C# / .NET Standard 2.1** —— 模组程序集的目标框架，即游戏 Mono 运行时能加载的那一档。
- **Unity 6000.3.25f1**、游戏 **3.4.0**（构建 **r150**）、**UnityModManager 0.33**。
- **Harmony** 做运行时方法补丁，含 Transpiler。
- **IMGUI 全自绘**设置界面：圆角九宫格底图、自绘滑条、开关与输入框——没有一个是原生控件。
- **ffmpeg** 作为外部编码器随模组分发：CPU 编码走 libx264，探到硬件编码器（NVENC）时回退可用。
- **离线闸门**：一个 `net10.0-windows` 离屏测试套件，链接真实的回放编解码与音频/格式逻辑，不启动游戏就能断言；外加一套变异测试——把每处修过的 bug 退回旧样子，验证断言真的会红。断言若无法变红，会被当作测试本身的 bug。

## 构建与安装

需要：.NET SDK **10.0 及以上**（解决方案文件 `SpectreReplay.slnx` 与 `net10.0-windows` 测试套件都要求 SDK 10），以及已安装游戏的托管程序集。

1. 把游戏的托管程序集（`Assembly-CSharp.dll`、`UnityEngine.*.dll`、`0Harmony.dll`、`UnityModManager.dll`、`Newtonsoft.Json.dll` 等）放进本仓库旁边的 `adofai-libs` 目录——项目文件就在那里找它们。它们以 `Private=false` 引用，绝不会被拷进构建输出。
2. 构建：

   ```sh
   dotnet build SpectreReplay/SpectreReplay.csproj -c Release
   ```

3. 安装：在游戏目录下建 `Mods\SpectreReplay\`，把这几样拷进去

   - `SpectreReplay.dll`（来自 `SpectreReplay/bin/Release/`）
   - `info.json`（来自项目目录——模组加载器靠它发现模组，缺了它 DLL 根本不会被加载）
   - `ffmpeg.exe`（可选，但视频渲染必须；查找顺序为模组目录 → 游戏根目录 → `PATH`）

4. 启动游戏，在 UnityModManager 里启用本模组，用热键呼出设置面板。

如果在游戏关闭时更新了 DLL，记得顺手删掉加载器留下的 `SpectreReplay.dll.*.cache*`——它下次启动会优先用那份缓存，否则跑的仍是上一个构建。
